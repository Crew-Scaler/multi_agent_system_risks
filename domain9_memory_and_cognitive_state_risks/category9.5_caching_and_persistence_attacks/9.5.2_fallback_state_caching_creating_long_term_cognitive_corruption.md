# 9.5.2 Fallback State Caching Creating Long-Term Cognitive Corruption [NoFW]

Graceful degradation logic that caches reduced-capability configurations as persistent state corrupts the agent's operational baseline across future normal-capability sessions.

When primary LLM providers become unavailable, graceful degradation logic switches to secondary providers and caches the degraded-mode configuration—reduced context window, simplified tool set, lowered validation thresholds—as persistent state so that subsequent warm-starts reload quickly. An attacker deliberately triggers repeated primary-provider failures (through rate-limit exhaustion or targeted denial-of-service) to force the system into fallback mode, then pre-poisons the fallback cache with a configuration that disables security-relevant validation steps; once cached, this degraded configuration is served as the trusted baseline during every subsequent fallback invocation. For example, an attacker exhausts an authentication service's rate limit, causing agents to cache a fallback config with credential verification disabled; the authentication service recovers, but agents continue loading the poisoned fallback config on warm restarts.

Standard defenses such as health-check monitoring are insufficient because the degraded-mode cache appears to contain valid operational configuration rather than malicious content, and recovery from fallback typically restores the cached state rather than revalidating it against a known-good source.

**Multi-agent distinction:** A single agent's fallback cache is scoped to its own session; in multi-agent systems sharing a common degradation configuration store, one poisoned fallback entry propagates the corrupted operational baseline to every agent that enters degraded mode, causing coordinated security capability loss across the entire pipeline simultaneously.
