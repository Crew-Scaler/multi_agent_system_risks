# 9.8.1 ETL State File Poisoning for Persistent Incremental Update Corruption [NoFW]

Corrupting the state files tracking ETL progress causes incremental updates to re-process or skip data in ways that systematically introduce malicious content into agent memory.

Incremental ETL pipelines use persistent state files (JSON storing last extraction timestamps such as `{"last_run": "2024-11-10T14:00:00Z", "sources": {"postgres": "2024-11-10T13:55:00Z"}}`) to determine which documents to fetch on each run; these files survive system restarts and are read by all agents sharing the ETL infrastructure. An attacker backdating the postgres timestamp to `2024-01-01T00:00:00Z` forces the next pipeline run to reprocess 10 months of historical data, flooding the vector database with millions of near-duplicate chunks that dilute retrieval precision; conversely, advancing the timestamp beyond the current date creates permanent knowledge gaps where documents updated in the intervening window are never ingested even after that date arrives.

Standard defenses such as file-level access controls on state.json are insufficient because the ETL process itself must hold write permission to update the state file on each successful run, and any attacker with access to the ETL execution environment can corrupt it without triggering schema or integrity validation since backdated timestamps are structurally valid JSON.

**Multi-agent distinction:** In a single-agent deployment, state file corruption affects only that agent's knowledge base; when multiple agents share a centralized state.json tracking collective ETL progress, one timestamp manipulation simultaneously creates synchronized knowledge gaps or duplicate floods across all agents in the fleet, achieving coordinated poisoning through a single file modification.
