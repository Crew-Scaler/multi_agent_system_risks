# 11.4.19 Asynchronous Configuration Updates During Multi-Agent Coordination [NoFW]

Configuration optimization happens asynchronously, creating windows where Agent A operates on old configuration while Agent B operates on new. Agent A's requests carry parameters calibrated for old configuration that Agent B interprets under different assumptions, producing silent behavioral inconsistencies invisible to both agents' validation.

Configuration management systems (Kubernetes ConfigMaps, Consul, etcd) propagate updates asynchronously via per-agent watch intervals; agents reload configuration on their own schedule, creating a window—potentially minutes long—where different agents in the same pipeline operate under different policy versions simultaneously, with no coordination signal between them. An attacker who can time a malicious request to coincide with the configuration transition window targets the behavioral gap: a request that the new configuration would block is accepted by an agent still running the old configuration, bypassing the update's security intent before it has fully propagated. For example, a configuration update tightens the maximum permitted output token length from 4096 to 512 to prevent prompt-stuffing exfiltration; Agent-A reloads the new configuration immediately while Agent-B has a 3-minute watch interval; during the 3-minute gap an attacker routes long-output requests specifically to Agent-B, which still enforces the 4096-token limit, obtaining outputs the updated policy was intended to prevent.

Standard defenses such as rolling configuration updates with health checks and feature-flag gating are insufficient because health checks verify agent availability, not configuration currency; agents that have not yet reloaded a new configuration pass all health checks while operating under a superseded policy, and the health check infrastructure has no visibility into which configuration version each agent is currently applying.

**Multi-agent distinction:** In MAS, agents with different watch intervals create a staggered configuration state across the pipeline; an adversary can profile the update propagation speed and exploit the gap between the first-to-update and last-to-update agent, targeting only the lagging agents in a way that is invisible in per-agent configuration logs because each agent reports a valid—if temporarily stale—configuration version from its own perspective.
