# 11.4.8 MLflow Version Mismatch Assurance Gap During Rollouts [NoFW]

MLflow deployments proceed at different times for different agents, creating mixed-version evaluation stores. Agent A writes v2.5-format artifacts that Agent B's v2.3 reader silently truncates or misparses, producing corrupted metric records both agents treat as valid and undermining audit verification.

MLflow artifact schemas evolve across minor versions without strict backward-incompatibility signals at the schema level; when agents at different MLflow client versions read from a shared experiment store, each applies its own version's schema, silently dropping or default-filling fields that exist only in newer artifact formats and emitting no parse error. An attacker who has write access to the shared MLflow store exploits the mixed-version window by inserting a poisoned artifact in v2.5 format; a v2.3-reading audit agent drops the v2.5-only security fields the artifact includes, applying defaults that cause the artifact to pass all gates the v2.5 fields were meant to enforce. For example, a risk-score artifact written by a v2.5 threat-intelligence agent includes a `confidence_interval` field used for threshold gating; a downstream audit agent still on v2.3 reads the artifact, silently drops the confidence field, applies a default that passes all risk gates, and approves an action the v2.5-computed confidence interval would have blocked.

Standard defenses such as artifact schema validation rules and version-pinned client dependencies are insufficient because MLflow's schema validation within the client is not enforced across minor version boundaries by default, and organizations frequently cannot pin all agents to the same MLflow version without disrupting rolling update workflows.

**Multi-agent distinction:** In MAS, the artifact store is a shared coordination surface that serializes information between agents; version skew between writing and reading agents means the same artifact produces different security-relevant parsed values depending on which agent reads it, creating a system where no single agent's local validation is authoritative for the actual data other agents will act on—a cross-agent integrity failure that a single-agent deployment with uniform client versions cannot produce.
