# 11.4.17 Hardware-Specific TensorRT Engine Variations Creating Deployment Assurance Gaps [NoFW]

TensorRT engines are GPU-architecture specific. Multi-agent fleet deployments across heterogeneous hardware (development RTX 4090, production A100) create different inference behaviors making pre-deployment safety testing on development hardware non-representative of production security posture.

TensorRT compiles neural network graphs into GPU-architecture-specific execution engines by selecting from a catalog of hardware-optimized kernels; the selected kernels differ in precision mode (FP32, FP16, INT8), memory layout (NHWC vs. NCHW), and layer fusion pattern, causing the same model weights to produce numerically distinct outputs depending on which GPU architecture compiled and runs the engine. An attacker who has characterized inference behavior on the production GPU architecture crafts inputs that exploit architecture-specific numerical properties—such as the INT8 calibration rounding on A100 but not on RTX 4090—to produce adversarial outputs that pre-deployment testing on development hardware would never trigger. For example, a security screening agent tested on RTX 4090 with FP16 TensorRT engines consistently blocks a specific prompt category; the production A100 fleet compiles to INT8 engines for throughput, changing the quantization rounding for that prompt category such that 3% of previously-blocked prompts score below the block threshold; the gap is invisible in development testing because TensorRT engine compilation is architecture-specific and the RTX 4090 and A100 engines select different INT8 calibration tables.

Standard defenses such as hardware-agnostic ONNX runtime and floating-point reproducibility flags are insufficient because TensorRT's throughput advantages require architecture-specific kernel selection and fusion decisions; disabling these optimizations to use a generic runtime changes the deployment's latency profile so fundamentally that it is no longer representative of the production engine being tested.

**Multi-agent distinction:** In MAS, agents may be deployed across a heterogeneous fleet where different agents run on different GPU architectures; an adversarial input that crosses a safety threshold on one architecture may not reproduce on another, making cross-agent audit replay unreliable and allowing exploits to succeed selectively against specific GPU-architecture agents while appearing benign in cross-agent testing conducted on a single reference architecture.
