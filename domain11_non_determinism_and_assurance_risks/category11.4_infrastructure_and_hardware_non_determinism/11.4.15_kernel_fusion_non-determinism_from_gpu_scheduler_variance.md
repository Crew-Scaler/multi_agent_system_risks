# 11.4.15 Kernel Fusion Non-Determinism From GPU Scheduler Variance [NoFW]

Kernel fusion execution order depends on GPU scheduler decisions varying based on load. Attackers craft inputs where model output depends on fusion execution order; one GPU's scheduling produces benign output while another produces malicious output, making cross-agent behavioral verification unreliable.

GPU kernel fusion merges multiple compute operations (matrix multiply, activation, layer normalization) into a single kernel for throughput efficiency; the merged kernel's internal execution order is determined at runtime by the GPU warp scheduler based on current SM occupancy and memory access patterns, causing accumulated floating-point rounding errors to depend on the scheduling variant chosen—a dependency that varies with GPU load and is not controllable by the application layer. An attacker analyzes the floating-point error surface of a target fused kernel across observed scheduling variants to identify inputs where variant A produces a safe continuation token with higher log-probability and variant B reverses the ordering; the attacker then submits requests during high-load periods when variant B is more probable, increasing the rate of adversarial continuation selection. For example, on an A100 under 80% SM occupancy a fused attention kernel executes under scheduling variant B, causing a particular adversarial continuation token's log-probability to exceed the benign alternative by 0.003 bits; at 30% occupancy the same kernel runs under variant A and produces the opposite ordering; the attacker times submissions to coincide with peak traffic windows to exploit the scheduling difference.

Standard defenses such as CUDA deterministic mode (`torch.use_deterministic_algorithms(True)`) and fixed random seeds are insufficient because deterministic mode disables kernel fusion entirely, imposing inference latency penalties that are prohibitive for production deployments; the only effective control eliminates the optimization that makes the deployment viable.

**Multi-agent distinction:** In MAS, agents running on different GPUs at different current load levels execute the same fused kernel under different scheduling variants; when agents compare outputs for cross-validation or reach consensus, kernel-fusion-induced divergence appears as genuine agent disagreement rather than infrastructure artifact, defeating consensus mechanisms that assume hardware-uniform computation across the agent fleet.
