# 11.4.10 StatefulSet Ordinal Initialization Races During Restart [NoFW]

StatefulSets initialize pods sequentially but network races during restarts create non-determinism in actual initialization order. Coordinated StatefulSet agents may initialize in non-deterministic order despite sequential specification, creating exploitable windows where dependent agents communicate with incompletely initialized peers.

For example, a three-agent consensus system deployed as a StatefulSet expects agent-0 to initialize first and publish a shared cryptographic nonce to a ConfigMap before agent-1 and agent-2 join; a network partition during restart causes agent-1's readiness probe to succeed 200 milliseconds before agent-0's nonce write completes, allowing agent-1 to initialize with a stale default nonce that an attacker who observed the race can predict and use to forge consensus messages.

Standard defenses such as StatefulSet OrderedReady pod management policies and init containers are insufficient because init containers complete their work before the pod's main container starts but before the pod's network service endpoint is registered by the Kubernetes endpoint controller; endpoint registration timing is determined independently of the StatefulSet sequencing policy, meaning a pod can become routable before its sequential predecessor's application state is visible on the network.

**Multi-agent distinction:** In MAS, a StatefulSet orchestrates agents that form an ordered trust boundary where each agent depends on predecessors completing initialization before joining; initialization races corrupt the trust establishment sequence for the entire multi-agent workflow, whereas a single-agent StatefulSet restart produces at most a self-consistency error contained within one pod rather than a cross-agent trust mismatch that propagates to all subsequent agents in the ordinal sequence.
