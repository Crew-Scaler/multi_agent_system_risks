# 11.4.1 Kubernetes Scheduler Indeterminism Creating Non-Reproducible Pod Placement [NoFW]

Non-deterministic pod placement decisions affect which physical resources agents use, producing different inference behavior from identical models due to hardware differences.

The Kubernetes scheduler applies scoring plugins that break ties non-deterministically among equally-ranked nodes, so agents assigned to different nodes may run on GPUs of different generations, NUMA configurations, or memory bandwidths, producing divergent floating-point results from mathematically identical model weights. An attacker who can influence node resource occupancy can steer agent placement toward hardware that produces output distributions favorable to an exploit—for example, by pre-occupying compute on nodes where the target agent would produce safe scores, forcing the scheduler to place it on a node where lower-precision arithmetic pushes a borderline safety score below the approval threshold. For example, an agent placed on an NVIDIA A100 node produces a safety score of 0.73 for an adversarial request while the same agent on a T4 node produces 0.69 due to FP16 vs. FP32 default precision differences; an attacker who learns that T4 placement yields sub-threshold scores can time submissions to coincide with A100 resource saturation events that redirect scheduling to T4 nodes.

Standard defenses such as fixed node affinity rules and replica-set uniformity are insufficient because Kubernetes scheduler tie-breaking among equally-scored nodes is inherently non-deterministic, and affinity rules cannot constrain which hardware generation occupies a given node after cloud-provider maintenance rotations or autoscaling events bring heterogeneous replacement hardware into the pool.

**Multi-agent distinction:** In MAS, each agent in a coordinating pipeline receives an independent scheduling decision, so a supervisor agent may land on one hardware generation while an executor agent lands on another; hardware-induced behavioral divergence between agents creates inconsistent risk assessments at different pipeline stages that neither agent can detect locally, whereas a single-agent deployment on one node experiences uniform hardware behavior throughout its lifecycle.
