# 11.1.1 Continual Framework Updates Invalidating Multi-Agent Security Assurance [NoFW]

Each framework update changes buffering, timing, error handling, or routing behavior, invalidating prior security testing without triggering re-evaluation requirements.

Framework update atomicity is the architectural property being exploited: when a framework updates, all agents sharing it change simultaneously, but the change itself is invisible to assurance processes. The attack mechanism is that vendors continuously update model weights, prompts, and routing logic within the same API endpoint, requiring re-evaluation of every agent combination when any component updates — yet the N(N-1)/2 pairwise combinations across an agent fleet make comprehensive re-testing prohibitive. A security team validates a five-agent pipeline against LangChain 0.2.1; LangChain releases 0.2.2, silently changing tool-call routing logic such that the pipeline continues to function correctly on benign inputs but the updated router now processes adversarial prompts differently, bypassing an injection filter that was validated against 0.2.1.

Standard defenses such as regression test suites are insufficient because they check known inputs against known outputs from the prior version, but framework updates change the input-to-output mapping in ways that are only detectable through exhaustive re-validation of every agent interaction that was previously certified.

**Multi-agent distinction:** In a single-agent system, one re-evaluation after a framework update suffices to restore assurance; in a multi-agent system, every pairwise interface between agents must be re-validated because Agent A on the new framework version may produce outputs that Agent B — still running the prior version or an intermediate update — interprets differently, creating cascading assurance gaps invisible to any individual agent's test suite.
