# 10.6.18 Service Account Token Reuse Across Agent Instances [NoFW]

Each Kubernetes pod receives service account tokens enabling API access. Attackers extracting tokens from one agent pod can impersonate that service account across all pod instances and machines, affecting any agent using that service account identity throughout the cluster.

Kubernetes service accounts exploit the property that tokens are cluster-scoped bearer credentials mounted into every pod sharing that account — meaning a token extracted from one pod is equally valid for authenticating as any other pod using the same service account. The attack mechanism involves extracting the mounted token from `/var/run/secrets/kubernetes.io/serviceaccount/token` on a compromised agent pod, then replaying it against the Kubernetes API server from any external location to authenticate as the service account identity. For example, an attacker who gains code execution on a single inference agent pod extracts its service account token, uses it from a remote host to enumerate cluster secrets, patch other agents' Deployment objects, or modify ConfigMaps supplying configuration to every agent in the fleet — all without any additional credential theft beyond the initial single-pod compromise.

Standard defenses such as short-lived projected tokens and TokenRequest API rotation are insufficient because tokens within their validity window are fully replayable from any source IP, and clusters frequently use long-lived default service account tokens that predate the projected-token feature; furthermore, shared service accounts across replicas mean revoking a token disrupts all agents simultaneously, creating operational pressure against rapid rotation.

**Multi-agent distinction:** In single-agent deployments, one service account token maps to one workload and its compromise is contained; in multi-agent fleets where all replicas of an agent type share a common service account, a single extracted token immediately authenticates as the identity of the entire agent pool, enabling an attacker to impersonate, reconfigure, or disrupt every agent sharing that credential without needing to compromise additional pods.
