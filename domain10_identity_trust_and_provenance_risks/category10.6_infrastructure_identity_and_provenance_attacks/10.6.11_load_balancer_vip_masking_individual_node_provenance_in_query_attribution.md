# 10.6.11 Load Balancer VIP Masking Individual Node Provenance in Query Attribution [NoFW]

Clustered vector database deployments use load balancers with virtual IP addresses that mask individual node identities, creating provenance gaps where audit logs cannot determine which specific node processed which agent's request. Attackers exploit this by compromising one node knowing that audit logs won't reveal the node identity, enabling persistent data exfiltration with attribution confusion across all agents sharing the load balancer.

For example, when Agent A queries the vector database through a load balancer VIP and node2 (compromised) handles the request, the database access log records the source as the load balancer IP rather than node2's IP, so when node2 is discovered compromised a week later during incident investigation, it is impossible to determine retrospectively which agents received poisoned search results from that node and which agent decisions were based on those results.

Standard defenses such as centralized logging and SIEM correlation are insufficient because the VIP abstraction is architectural: the load balancer terminates the connection and initiates a new one to the backend, stripping the original source information before the backend node's logs are written, and most load balancer configurations do not log which backend node served each request.

**Multi-agent distinction:** Single-agent deployments connecting directly to database nodes maintain node-level attribution in access logs; multi-agent systems routing through shared load balancer VIPs lose per-request node attribution for all agents simultaneously, creating audit gaps that prevent forensic reconstruction of which agents were exposed to any specific compromised node's output.
