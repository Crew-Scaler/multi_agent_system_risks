# 12.4.18 Trace Filtering as Selective History Manipulation [NoFW]

Trace filtering tools become attack vectors in multi-agent systems when attackers exploit filtering by poisoning span metadata. Attackers cause critical tool invocations to appear as non-error spans that filtering removes from oversight views, hiding evidence of unauthorized executions from downstream agents querying filtered traces. Unlike singular trace filtering affecting one agent's analysis, shared multi-agent trace repositories enable one metadata poisoning to affect all trace consumers simultaneously.

For example, an attacker who has compromised an agent's tool invocation layer modifies span metadata to tag unauthorized API calls with `status: "info"` and `service: "health-check"`, causing trace filtering rules designed to remove routine health-check spans to silently purge evidence of the malicious invocations from the trace repository before any security analyst reviews them; the filtering operates on the poisoned metadata and the true content of the malicious spans is never committed to the permanent audit record.

Standard defenses such as append-only trace storage, trace signing, and immutable audit logs are insufficient when the metadata poisoning occurs upstream of the write operation, because the filtering rule consumes the manipulated metadata and discards the span before any integrity protection can be applied to a record that is never written.

**Multi-agent distinction:** In single-agent deployments trace filtering operates on one agent's span stream, limiting the blast radius of metadata poisoning to that agent's trace visibility; in multi-agent shared trace repositories, a single metadata poisoning pattern applied to one agent's spans establishes a filtering precedent that silently removes matching spans from all agents sharing the same filtering rule configuration—multiplying the evasion effect across the fleet from a single point of manipulation without requiring access to any other agent.
