# 12.1.6 Error Recovery Telemetry Treating Retry Attempts as Atomic Events [NoFW]

Automatic retry mechanisms log each attempt as an independent event rather than as a sequence, preventing detection of attacks that deliberately trigger errors to force specific retry code paths or that exploit different security contexts across retry attempts.

For example, an attacker crafts a request that causes Agent A to fail on the first attempt, triggering Agent B's error-recovery handler with elevated permissions granted for the retry context; the third retry succeeds and executes unauthorized privilege escalation, but telemetry records three independent events ("attempt 1 failed," "attempt 2 failed," "attempt 3 succeeded") with no log entry capturing that retry attempt 3 operated under a different security context than the original request or that different agents handled different attempts.

Standard defenses such as idempotency tokens and per-attempt action logging are insufficient because they treat each retry as structurally equivalent to the original request, failing to capture that error-recovery code paths may invoke different agents with different credential scopes, skip validation steps omitted for efficiency in retries, or operate with escalated permissions that the original attempt would never have received.

**Multi-agent distinction:** In single-agent systems retry logic is local and a security review can inspect all code paths in one place; in multi-agent error recovery each retry may route through a different specialist agent (detection, diagnosis, coordination, execution) with its own distinct security context, and the absence of sequence-level telemetry that treats the entire retry chain as a unit makes the composite retry trajectory invisible as an object of security analysis.
