# 12.3.31 State File Modification Tracking Gaps Hiding Unauthorized Timestamp Manipulation [NoFW]

ETL pipeline state files tracking last-run timestamps are monitored for existence but not content integrity; adversaries with filesystem access can roll back timestamps to force re-ingestion of historical data or advance timestamps to skip future updates, and monitoring systems that log only "state file updated successfully" cannot distinguish authorized from unauthorized state file modifications.

For example, an attacker with filesystem write access rolls back the ETL state file timestamp from 2024-11-10 to 2024-11-01, causing the next incremental run to re-ingest nine days of historical documents and create thousands of duplicates; monitoring logs "state file updated successfully" and reports a run processing an unusually high document count, which operators dismiss as a backlog catch-up rather than investigating the unauthorized timestamp rollback.

Standard defenses such as filesystem access controls and ETL run logging are insufficient because access controls prevent unauthorized processes from writing the file but do not prevent authorized ETL processes acting on corrupted state, and run logs record that the file was updated without capturing before-and-after content diffs that would reveal a rollback.

**Multi-agent distinction:** In multi-agent systems where many agents share centralized ETL state files, attribution of any unauthorized modification to a specific agent becomes impossible without per-agent write provenance; file locking prevents concurrent writes but does not prevent any authorized agent process from overwriting state with an adversarially manipulated value, and a single corrupted state file causes every agent's next incremental run to behave incorrectly.
