# 12.5.79 Queue Depth Metrics Blind Spot in Multi-Agent Orchestration [NoFW]

Inference serving queue depth metrics reflect infrastructure queuing but not orchestration-level queuing in multi-agent workflows; when agents queue requests to other agents upstream of the inference server, orchestration-layer bottlenecks and deadlocks appear in monitoring as healthy inference queue depths that do not reflect the true multi-agent queuing state.

For example, an attacker who introduces artificial processing delays in an orchestration agent causes downstream execution agents to queue their inference requests at the orchestration layer rather than at the inference server; the inference server queue depth remains near-zero (indicating apparent health), the execution agents appear idle (low utilization), while the orchestration queue grows unboundedly—an orchestration-layer deadlock that no standard Kubernetes or Prometheus alert detects because the relevant queue depth exists entirely in application-layer state.

Standard defenses such as Kubernetes resource utilization alerts and Prometheus queue depth metrics are insufficient because they instrument infrastructure-layer queuing constructs such as HTTP request queues and message broker offsets, not the application-layer coordination queues that multi-agent orchestration frameworks implement through in-memory data structures or agent-specific messaging protocols.

**Multi-agent distinction:** In a single-agent system, queuing occurs at the well-instrumented infrastructure boundary between the user and the agent; in a multi-agent workflow, additional queuing layers emerge at every agent-to-agent boundary, none of which are automatically instrumented by standard observability stacks, creating measurement blind spots proportional to pipeline depth.
