# 12.5.71 Kubernetes API Server Audit Log Cardinality Overload [NoFW]

High API call frequency in multi-agent Kubernetes deployments (frequent status updates, service lookups, ConfigMap reads across many agents) creates audit log volumes that operators disable or heavily sample to manage storage costs; adversaries who understand that detailed audit logging has been disabled or sampled route privileged operations to exploit the reduced audit coverage.

For example, a 100-agent deployment generates thousands of API calls per second to the Kubernetes API server for health checks, service discovery, and ConfigMap reads; to manage the resulting audit log volume operators enable only "Metadata" level logging that captures resource type and caller identity but omits request and response bodies, so when an attacker exploits a compromised agent to escalate cluster privileges through a series of Role and ClusterRoleBinding modifications, each modification is logged only as "RBAC resource modified by service-account-X" without the specific permissions granted.

Standard defenses such as tiered audit policies and log sampling are insufficient because privilege-escalation attacks typically generate only a handful of API calls that are identical in structure to legitimate administrative operations, making rule-based filtering unable to distinguish attack traffic from the high-volume legitimate traffic that motivated the audit reduction in the first place.

**Multi-agent distinction:** In a single-agent deployment, Kubernetes API call volume is manageable enough to sustain comprehensive audit logging; in a multi-agent fleet, the aggregate API call rate scales linearly with agent count, creating operational pressure to reduce audit coverage that is unique to multi-agent architectures and not present in single-agent deployments.
