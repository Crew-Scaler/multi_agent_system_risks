# 13.5.19 Triton Continuous Batching Request Substitution Attacks Through Malicious Slot Injection [NoFW]

Triton Inference Server's continuous batching dynamically allocates inference compute slots to incoming requests, enabling attackers to inject carefully timed requests that claim compute slots during high-load periods when slot allocation mechanisms operate under degraded validation. Attacker-controlled requests occupying critical inference slots can influence shared batch-level computations through co-batch attention mechanisms, substituting attacker-controlled inputs into inference slots that victim requests expect to occupy exclusively. In multi-agent Triton deployments, slot injection attacks exploit shared inference infrastructure affecting all agents whose requests are batched in the same continuous batching window.

Standard defenses such as queue-based fairness scheduling and request authentication are insufficient because continuous batching slot allocation operates on latency-optimization heuristics at the microsecond level, where cryptographic authentication per slot assignment would eliminate the throughput benefit that justifies continuous batching; the allocation decision must be made faster than any per-slot validation can execute, leaving slot assignment dependent on timing rather than verified identity.

**Multi-agent distinction:** Single-agent Triton deployments allocate inference slots exclusively to one tenant's requests, providing no co-tenant surface for slot injection. Multi-agent shared Triton infrastructure pools inference slots across all agents' requests in real time, so one agent's timed high-load injection can claim slots intended for other agents, and co-batch attention mechanisms allow the injected request to influence token generation for victim requests occupying adjacent slots in the same continuous batching window.
