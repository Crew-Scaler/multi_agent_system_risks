# 13.5.2 GPU Embedding Resource Exhaustion Through Adversarial Batch Flooding [NoFW]

Flooding GPU embedding queues with computationally expensive inputs degrades embedding generation for all agents sharing the infrastructure.

GPU-accelerated embedding services (e.g., NV-Embed-v2 with a 32,768-token context limit) batch concurrent requests to maximize GPU memory utilization; when requests are maximum-length, memory constraints collapse the effective batch size from 32 short queries to 2 long queries, forcing sequential processing and reducing throughput from 320 documents per second to 15 documents per second while increasing latency from 35 ms to 450 ms for every co-tenant agent. For example, an attacker controlling one low-privilege document-ingestion agent submits a continuous stream of 32K-token documents to the shared embedding endpoint; within seconds, the GPU's batch scheduler degrades to serial execution, stalling all other agents awaiting embeddings for unrelated user queries. Because the shared GPU endpoint imposes no per-agent bandwidth quota, the malicious agent legally exhausts the collective compute budget without triggering any per-request rate limit.

Standard defenses such as per-request token caps and rate limiting per API key are insufficient because a single agent submitting maximum-allowed-length requests at a legal rate can still force sequential GPU execution that dominates shared memory, and token-level rate limits do not constrain the memory footprint of in-flight batches shared across all co-tenant agents.

**Multi-agent distinction:** In a single-agent deployment, resource contention from large requests affects only that agent's own embedding latency. In multi-agent shared GPU infrastructure, one agent's adversarial batch flooding collapses throughput for the entire fleet simultaneously, converting a bounded self-inflicted slowdown into a fleet-wide denial of service with no architectural isolation between co-tenant agents.
