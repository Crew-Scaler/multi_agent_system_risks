# 13.5.11 Init Container Model Download Hijacking [NoFW]

Kubernetes init containers downloading model weights from external registries (NGC, HuggingFace, S3) before main agent containers start are vulnerable to supply chain attacks at the download layer. Attackers performing man-in-the-middle attacks on model download connections, poisoning DNS to redirect downloads to attacker-controlled endpoints, or compromising external registry contents cause init containers to download adversarial model weights before the main agent container's security controls activate. In multi-agent Kubernetes clusters, all pods using the same init container specification download from the same endpoint, enabling one supply chain compromise to affect all cluster deployments simultaneously.

Standard defenses such as TLS certificate verification and registry content trust policies are insufficient because DNS poisoning attacks operate below TLS hostname validation by redirecting before the TLS handshake resolves the legitimate certificate, and registry content trust only protects against unsigned artifacts—attackers who compromise the upstream registry itself can sign malicious weights with the registry's own key, passing signature verification transparently.

**Multi-agent distinction:** Single-agent deployments can use pod-specific download credentials and unique registry endpoints per agent instance, limiting supply chain compromise to one pod's init phase. Multi-agent Kubernetes clusters sharing a common init container specification pull from the same registry endpoint under the same credentials, so one poisoned registry path simultaneously delivers adversarial model weights to every pod in the cluster before any main container security control activates.
