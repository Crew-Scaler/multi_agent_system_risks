# 13.5.7 Kubernetes Secret Store Poisoning for Shared Agent Credentials [NoFW]

Kubernetes secrets storing NGC API keys and other shared credentials (used by all NIM/agent pods) can be poisoned if attackers gain write access to the secret store (etcd). Compromising one shared secret affects all agent services authenticating through it. Unlike singular deployments with independent credentials, multi-agent Kubernetes deployments using shared secrets enable single-secret-poisoning attacks propagating to all agents simultaneously, converting centralized credential management from an operational convenience into a single point of fleet-wide failure.

For example, an attacker who compromises a single CI/CD service account with etcd write permissions can replace all agent pods' NGC API key secrets with attacker-controlled credentials in one operation, causing every NIM pod across the fleet to authenticate to an attacker-controlled model registry on next restart—without any per-agent compromise and without any alert from normal secret-access audit logs that record the write as a legitimate administrative action.

Standard defenses such as Kubernetes RBAC policies and audit logging are insufficient because once etcd write access is obtained, secret overwrite operations appear as legitimate administrative changes, and agents validate credentials only at startup, so the substitution goes undetected until poisoned credentials cause authentication failures or unexpected model behavior that operators attribute to registry issues rather than secret tampering.

**Multi-agent distinction:** Single-agent deployments can use unique, rotation-isolated credentials per instance, limiting blast radius to one compromised agent and enabling precise revocation. Multi-agent Kubernetes deployments sharing Secrets for operational convenience allow one etcd write to simultaneously poison credentials for the entire fleet, converting the efficiency benefit of centralized secret management into a single-point-of-compromise that propagates instantly to all agents without requiring individual agent access.
