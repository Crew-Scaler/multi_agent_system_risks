# 13.5.9 Cross-Agent Filesystem Sharing Through Volume Mount Misconfiguration Enabling Information Leakage [NoFW]

Production containerized multi-agent deployments using shared Kubernetes PersistentVolumeClaims with misconfigured filesystem permissions (default 755 instead of 700, or all containers running as the same UID) enable any agent container to read and write any other agent's directory. Attackers compromising one lower-privilege agent can scan all 45 agent directories in 30 seconds, harvesting cached database credentials from 40% of the fleet and achieving fleet-wide lateral movement. Malicious file injection via shared volume access can backdoor all agent startup scripts, persisting through container restarts and Kubernetes rolling updates. Single-agent dedicated PVCs eliminate this cross-agent attack surface entirely.

Standard defenses such as Kubernetes NetworkPolicy and container SecurityContext restrictions are insufficient because PVC filesystem permissions are governed by the container runtime's UID/GID mapping at mount time, and default configurations commonly assign the same UID to all containers mounting the same PVC, granting any one agent read-write access to every sibling agent's mounted directory regardless of network isolation policies applied at a higher layer.

**Multi-agent distinction:** Single-agent deployments with dedicated PVCs have no shared filesystem surface accessible to other agents, so filesystem-level compromise is bounded to the one compromised instance. Multi-agent shared PVC deployments create a lateral movement highway where compromising any single agent grants filesystem access to all co-mounted agent directories, allowing one low-privilege agent compromise to harvest credentials and backdoor startup scripts for the entire fleet in a single reconnaissance sweep.
