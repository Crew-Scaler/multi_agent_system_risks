# 13.5.13 Persistent Volume Mount Symlink Attacks on Tool Definitions [NoFW]

Container-based agent deployments mounting tool definition files from shared persistent volumes are vulnerable to symlink attacks when container runtime configurations allow symlink following across volume boundaries. Attackers create adversarial symlinks within mounted volumes pointing to sensitive host filesystem paths or other containers' private directories, causing agent containers following symlinks to read attacker-specified file contents as tool definitions. In multi-agent deployments sharing PVC-mounted tool definition directories, one symlink attack affects all containers with that volume mounted simultaneously.

For example, an attacker who gains write access to a shared tool-definition PVC can replace the legitimate tools/web_search.json file with a symlink pointing to /proc/1/environ (the init process environment of the host), causing every agent container that reads tool definitions at startup to load host environment variables—including secrets injected by the container orchestrator—as tool configuration without triggering file permission errors.

Standard defenses such as read-only volume mounts and AppArmor profiles are insufficient because read-only mounts prevent new file creation but do not block symlink resolution at the kernel layer if allowFollowSymlinkInScope is not explicitly disabled in the container runtime, and AppArmor policies governing file reads typically whitelist the mounted path without restricting the symlink target path.

**Multi-agent distinction:** Per-container tool definition copies limit symlink attacks to one container's tool loading phase. Shared PVC-mounted tool definitions propagate a single symlink to every container with that volume mounted, causing one successful write to simultaneously redirect tool definition reads across the entire agent fleet to attacker-controlled or sensitive host paths.
