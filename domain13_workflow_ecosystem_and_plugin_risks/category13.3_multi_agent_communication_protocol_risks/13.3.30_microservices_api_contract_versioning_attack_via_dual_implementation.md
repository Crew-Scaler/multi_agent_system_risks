# 13.3.30 Microservices API Contract Versioning Attack via Dual Implementation [NoFW]

Microservice deployments supporting multiple API versions simultaneously for backward compatibility maintain both legacy and current implementations. Agents connecting to microservices in multi-agent orchestration workflows may target deprecated API versions with known security vulnerabilities or relaxed validation, bypassing security improvements applied to current versions while remaining within the service's supported interface surface. In multi-agent systems where different agents pin to different API versions for compatibility, version-specific attacks exploit the heterogeneous API contract landscape created by rolling upgrades without simultaneous deprecation enforcement, enabling attackers to route agent workflow traffic through vulnerable legacy API endpoints.

For example, in a multi-agent order fulfillment system where a payment agent uses the current v3 API endpoint with enforced token authentication while an inventory agent was never updated and still targets the legacy v1 endpoint lacking token validation, an attacker who discovers this discrepancy can craft requests that masquerade as inventory updates to inject unauthorized payment instructions through the unauthenticated v1 path, exploiting the privilege available through the inventory agent's vulnerable API version.

Standard defenses such as deprecation schedules and versioning policies are insufficient because they specify when legacy versions will be removed but do not actively prevent consumption of those versions until the sunset date; agents that are difficult to update due to dependency constraints continue using deprecated endpoints that remain available, and the policy itself does not close the security gap during the deprecation window.

**Multi-agent distinction:** API versioning attacks are uniquely dangerous in multi-agent systems because different agents may legitimately target different API versions for compatibility reasons, creating a heterogeneous version landscape where the attacker can identify the weakest version in use and route workflow traffic through whichever agent targets it; in a single-agent system only one API version is active, so operators can enforce a single consistent security posture rather than managing a mixed landscape of version-specific vulnerabilities.
