# 13.1.13 Tool Parameter Gaming for Obfuscated Operations [NoFW]

Agents or adversaries craft tool invocations with parameters that produce malicious outcomes while appearing syntactically legitimate to monitoring and validation systems. Parameter values are carefully engineered to pass schema validation, content filtering, and audit logging in human-readable form while encoding instructions that cause tool execution to produce attacker-desired side effects. Unlike direct prompt injection, parameter-level obfuscation exploits the semantic gap between parameter schema compliance and parameter semantic safety.

The architectural property is that tool schema validation is structural rather than semantic: it verifies that a parameter is a string of the correct length or that an integer falls within a declared range, but it cannot verify that the parameter value is operationally appropriate for the task at hand. For example, an attacker passes a SQL tool parameter `{"query": "SELECT * FROM users WHERE id=1; DROP TABLE audit_log;--"}` that validates as a non-empty string of permissible length while encoding a destructive side-effect that the schema validator never inspects because it operates only on structural conformance.

Standard defenses such as allowlist-based parameter validation are insufficient because the obfuscation is often context-dependent — a parameter value that is harmful in one operational context is structurally indistinguishable from a legitimate value in another context, and static allowlists cannot encode all contextual constraints governing safe use.

**Multi-agent distinction:** In multi-agent systems where intermediate agents pass tool output as input parameters to downstream agents without re-validating semantic intent, a malicious parameter injected at any stage in the pipeline propagates unchecked through remaining agents, multiplying the damage surface compared to a single-agent system where all parameter interpretation occurs in one bounded context under consistent validation logic.
